# Стек и архитектурные решения

**Статус:** выбранный стек для MVP; картографические функции — запланированное расширение.

## 1. Цель проекта и границы MVP

Сервис публикуемых поездок между одной **фиксированной точкой** и второй точкой, которую пользователь указывает как район из справочника или полный адрес. В MVP пользователь **сам просматривает и выбирает поездку**, без алгоритма автоматического матчинга и без расчёта реального дорожного маршрута.

Планируемые экраны: список/фильтры поездок, детали поездки, форма создания поездки; позднее — заявки и профили.

Один демонстрационный сквозной сценарий для практики 8: **заполнение формы → создание поездки через реальный API → появление новой поездки в списке**.

## 2. Зафиксированные технологии

| Зона | Выбор | Статус / роль |
|---|---|---|
| Фронтенд | React + TypeScript | Основной UI и типы |
| Сборка / dev server | Vite | SPA без обязательного SSR |
| Стили | Tailwind CSS | Общие цвета, типографика и отступы |
| UI-компоненты | shadcn/ui | Кнопки, поля, диалоги, карточки; исходники в проекте |
| API | Python + FastAPI | HTTP API, доменная логика, серверная валидация |
| БД | PostgreSQL | Постоянное хранение пользователей, районов, поездок, заявок |
| Генерация AI-макета | v0 | Прототип и визуальный ориентир; код адаптировать под Vite |
| AI-разработка | VS Code + Codex | Необязательно: разработчик может писать вручную |
| Отладка UI | Playwright MCP, Chrome DevTools MCP | Действия браузера, сеть, консоль; не заменяют тесты |
| Юнит-/компонентные тесты | Vitest + React Testing Library | Логика UI и пользовательские взаимодействия |
| E2E / скриншоты | Playwright Test | Сквозные сценарии и визуальные регрессии |
| Доступность | axe-core + ручная проверка | Подписи, фокус, клавиатура, контраст |
| Автоматизация разработки | n8n + GitHub API + LLM | PR-review, Issues, статистика; **вне пользовательского API** |
| Карта (позднее) | MapLibre GL JS | Отображение географических точек и маршрута |
| Геокодирование/маршрутизация (позднее) | Отдельные внешние сервисы; провайдер не выбран | Адрес → координаты, дорожный путь |

**Не выбраны для MVP:** Next.js/SSR, Lovable/Replit как обязательная runtime-платформа, Redux, Redis, PostGIS, микросервисы, авто-матчинг маршрутов. Пересмотреть только после появления конкретного требования.

## 3. Архитектура

```text
Browser
  └─ React + TypeScript + Vite
       ├─ screens / components (shadcn/ui + Tailwind)
       ├─ domain types
       └─ typed HTTP client
            └─ FastAPI
                 └─ PostgreSQL

GitHub (PRs / Issues)
  └─ n8n workflows + LLM (developer tooling; independently from app)

Future: React → MapLibre GL JS (rendering); API → geocoding / routing provider
```

**Разделение ответственности:** React отображает данные и принимает ввод, FastAPI проверяет правила и управляет поездками, PostgreSQL хранит состояние. n8n не подключается к маршруту обычного пользовательского запроса.

## 4. Данные с учётом будущей карты

Минимальные концептуальные модели (не фиксируют окончательную схему БД):

- `Area`: идентификатор, название района.
- `Location`: тип (`area` или `address`), район, опциональный адрес, опциональные `latitude` / `longitude`.
- `Trip`: идентификатор, автор, направление относительно фиксированной точки, вторая точка, время отправления, число мест, статус.
- `Booking` (отдельный следующий этап): заявка пользователя на поездку и её статус.

Одна фиксированная точка задаётся серверной конфигурацией/справочником, а не дублируется вручную во всех формах. Точные адреса должны иметь отдельно определённые правила видимости. В перспективе поддержать геометрию маршрута, **не** делая её обязательным полем MVP.

## 5. Минимальный HTTP-контракт (предложение, уточняется перед реализацией)

- `GET /areas` — варианты районов.
- `GET /trips?area_id=...&direction=...&from=...&to=...` — список поездок с фильтрами.
- `POST /trips` — создание поездки.
- `GET /trips/{id}` — детали поездки.
- Позднее: заявки на поездку и управление ими.

Контракт **предлагаемый, а не существующий**: до интеграции фронтенда согласовать поля/форматы с реализацией FastAPI. В тестах mock API должен отвечать в том же формате.

## 6. Стандарты UI и критерии приёмки

- Компоненты shadcn/ui переиспользуются; единые цвета, шрифты, отступы.
- Все поля имеют подписи; доступно управление с клавиатуры и виден фокус.
- Форма: валидация обязательных/некорректных значений, индикатор отправки, блокировка повторных запросов.
- Обязательные состояния: загрузка, пустые данные, успех, ошибка; при ошибке форма не теряет введённые значения.
- Есть автоматические проверки действий пользователя и результата, а не только наличия элементов.
- Тестирование API на клиенте использует моки: успех / пустой ответ / задержка / ошибка; демонстрация — реальный backend.
- Снимки Playwright обновляются **после** проверки изменений человеком, не автоматически ради прохождения теста.

## 7. Процесс разработки и PR

```text
issue/spec → implementation (human or AI) → PR
                ↓
             review (CI + AI + human)
                ↓
       defects? ── yes → fix → tests/review again
                └── no  → merge → next issue
```

**Практика 7.1:** n8n реагирует на GitHub PR/комментарии; `/make_ai_review` и `/make_other_ai_review` — две модели, Data Table хранит проверенные PR, повторный `/make_ai_review` для уже проверенного PR блокируется. Точечные комментарии — отдельное расширение. Возможные будущие `/fix_ai_review` и `/rerun_ai_review` не должны ломать эту обязательную семантику; при повторном ревью версии diff учитывай `head_sha` отдельно от обязательной дедупликации по PR.

**Практика 7.2:** отдельный workflow классифицирует `issues.opened` (`bug` / `task` / `feature`), `confidence < 0.8` / неизвестный тип → `needs-triage`; отдельный sub-workflow классификатора; отчёт по недельной статистике через Gmail. AI-фиксы по bug report — только возможный бонусный workflow, не часть пользовательского приложения.

**Практика 8:** создаётся или дорабатывается AI-прототип, документируются выбранные компоненты, подключается реальный API/логика, тестируются видимые действия и состояния, сохраняются исходники, результаты тестов и описание участия AI.

## 8. Приоритеты реализации

1. Репозиторий, спецификация, базовый React/Vite и FastAPI.
2. AI-макет и согласование внешнего вида.
3. Список поездок и фильтры на фронтенде.
4. Создание поездки; соединение с реальным API и БД.
5. Валидация, ошибки, тесты, адаптивность, доступность.
6. n8n AI-ревью и автоматизация Issues (отдельный контур разработки).
7. Позднее: заявки/профили, геокодирование, отображение карты, маршрутизация.
