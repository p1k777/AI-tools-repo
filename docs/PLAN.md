# План разработки: сервис поиска попутчиков

**Статус:** черновик для реализации MVP и учебных практик 7.1 / 7.2 / 8.

## 1. Цель и рамки

Веб-сервис публикуемых поездок: одна **фиксированная конечная точка** (задаётся серверным справочником) и вторая точка, которую пользователь указывает как район из справочника или полный адрес. В MVP пользователь сам просматривает и выбирает поездку через фильтры; **нет** автоматического матчинга и **нет** расчёта реального дорожного маршрута.

**Сквозной демонстрационный сценарий (практика 8):** заполнение формы → создание поездки через реальный FastAPI → появление новой поездки в списке.

**Не входит в MVP:** карта/MapLibre, геокодирование, маршрутизация, PostGIS, Redis, Next.js/SSR, Redux, микросервисы, авто-матчинг, публикация точных адресов всем пользователям.

## 2. Исходное состояние репозитория

- Кода приложения **нет**: только `README.md`, `AGENTS.md`, `docs/tech-stack.md`, `opencode.json`, `.gitignore`.
- Стек и границы зафиксированы в `docs/tech-stack.md`; изменения архитектуры — через обновление этого файла.
- Git-репозиторий инициализирован, история — тестовые коммиты.

**Первый шаг до кода:** создать структуру каталогов и каркасы frontend (`client/`) и backend (`server/`), не вводя лишних зависимостей.

## 3. Целевая структура проекта

```text
/

│  │  ├─ features/       # trips/ (список, форма, детали)
│  │  ├─ lib/            # http.ts — единый HTTP-клиент, api.ts
│  │  ├─ types/          # доменные TypeScript-типы
│  │  └─ screens/        # страницы/роуты
│  └─ tests/
├─ server/               # Python + FastAPI
│  ├─ app/

│  │  ├─ models/         # SQLAlchemy-модели (Area, Location, Trip)
```

## 4. Модель данных (концептуальная, уточняется при схеме БД)

- `Area`: `id`, `name` — район из справочника.
- `Location`: тип `area` | `address`; для района — ссылка на `Area`; для адреса — `address` (полный) и **опциональные** `latitude` / `longitude` (под будущую карту, не обязательны в MVP).
- `Trip`: `id`, `author`, `direction` (относительно фиксированной точки), вторая `Location`, `departure_at`, `seats`, `status`.
- `Booking` — следующий этап, в MVP не реализуется.
- Фиксированная точка — серверная конфигурация/справочник, **не** дублируется в формах.
- Видимость точных адресов — отдельные правила (по умолчанию скрыты/ограничены).

## 5. Этапы реализации

> Каждый этап — один или несколько небольших логически цельных PR по правилу «одна задача — один PR».

### Этап 0. Каркас проекта
- [ ] Создать `client/` (Vite + React + TS, Tailwind, shadcn/ui) и `server/` (FastAPI + SQLAlchemy + PostgreSQL).
- [ ] Настроить `docker-compose.yml` для PostgreSQL (локальная разработка).
- [ ] Добавить `.env.example` (без секретов) и расширить `.gitignore`.
- [ ] Проверка: `client` собирается (`npm run build`), `server` стартует, `/health` отвечает.
- [ ] Обновить `docs/tech-stack.md`, если выбрана схема `client/` + `server/`.

### Этап 1. Бэкенд: данные и API
- [ ] Модели `Area`, `Trip` (+ `Location` как встроенная структура) и миграции.
- [ ] Сид справочника районов и фиксированной точки.
- [ ] Эндпоинты (предложение из tech-stack, уточнить поля при реализации):
  - `GET /areas` — список районов;
  - `GET /trips?area_id=&direction=&from=&to=` — фильтры;
  - `POST /trips` — создание;
  - `GET /trips/{id}` — детали.
- [ ] Серверная валидация (обязательные поля, диапазоны, статусы) и обработка ошибок (422/404/409).
- [ ] Правила видимости точного адреса на сервере.
- [ ] Тесты API (pytest + TestClient): успех, пустой ответ, ошибки валидации.
- [ ] Обновить контракт в `docs/tech-stack.md` (раздел 5) после согласования полей.

### Этап 2. Фронтенд: базовые типы и HTTP-клиент
- [ ] Доменные TS-типы (`Area`, `Trip`, `Location`, фильтры) в `src/types`.
- [ ] Единый HTTP-клиент `src/lib/http.ts` и `src/lib/api.ts` — источник запросов, без моков в прод-коде.
- [ ] `GET /areas` и `GET /trips` в api.ts.
- [ ] Тесты клиента (Vitest): моки успеха / пустого ответа / задержки / ошибки.

### Этап 3. Фронтенд: AI-макет и дизайн-система (практика 8)
- [ ] Подготовить AI-макет (v0 или экспорт макета) как визуальный ориентир, **не** источник бизнес-логики.
- [ ] Сохранить ссылку/экспорт макета в `docs/practice-08/`.
- [ ] Согласовать внешний вид: цвета, типографика, отступы — через Tailwind-токены и shadcn/ui.
- [ ] Зафиксировать, что предложил AI и что исправили по итогам ревью (артефакт для практики 8).

### Этап 4. Фронтенд: список поездок и фильтры
- [ ] Экран списка `screens/TripList.tsx` + компоненты `features/trips/`.

- [ ] Карточка поездки: направление, вторая точка (без раскрытия полного адреса по умолчанию), время, места.
- [ ] Тесты компонентов (RTL): успех, пустой список, ошибка, применение фильтров.

### Этап 5. Фронтенд: создание поездки
- [ ] Форма `features/trips/TripForm.tsx`: вторая точка (район из справочника ИЛИ полный адрес), направление, время, места.
- [ ] Валидация обязательных/некорректных полей; подписи у всех полей.
- [ ] Индикатор отправки; блокировка повторной отправки (двойной клик / Enter).

- [ ] `POST /trips` через api.ts; после успеха — редирект в список/детали.

### Этап 6. Детали поездки
- [ ] Экран `GET /trips/{id}`: полная информация, корректная видимость адреса.

### Этап 7. Сквозной сценарий и E2E (практика 8)

## 6. Практики 7.1 и 7.2 (автоматизация разработки, n8n)

> Отдельный контур разработки, **вне пользовательского API** приложения.

- [ ] **7.1:** n8n workflow на события GitHub PR/комментариев.
  - `/make_ai_review` — первоначальное ревью с дедупликацией проверенных PR (Data Table хранит проверенные PR; повторный вызов для того же PR блокируется).
  - `/make_other_ai_review` — ревью другой моделью.
  - Учитывать `head_sha` отдельно от дедупликации по PR при повторном ревью версии diff.
  - `/fix_ai_review` и `/rerun_ai_review` — необязательные будущие расширения; не ломают обязательную семантику дедупликации.
- [ ] **7.2:** workflow классификации `issues.opened` (`bug` / `task` / `feature`); `confidence < 0.8` или неизвестный тип → `needs-triage`; отдельный sub-workflow классификатора; еженедельная статистика через Gmail.
- [ ] Артефакты workflow сохранить в `.n8n/`, схемы — в документации.

## 7. Стандарты UI и критерии приёмки (для каждого экрана)

- Компоненты shadcn/ui переиспользуются; нет дублирования компонентов/токенов.
- Все поля подписаны; управление с клавиатуры, видимый фокус.
- Формы: валидация обязательных/некорректных значений, индикатор отправки, блокировка повторных запросов.
- Обязательные состояния: `loading` / `empty` / `success` / `error`; при ошибке форма сохраняет ввод.
- Тесты проверяют наблюдаемое поведение, а не только наличие элементов.
- Клиентские тесты подменяют API моками; демонстрация — реальный backend.

## 10. Риски и открытые вопросы

- **Контракт API** — предлагаемый; поля/форматы согласовать до интеграции фронтенда (Этап 1 перед Этапами 4–5).
- **Фиксированная точка** — определить, как хранится и передаётся клиенту (серверный справочник/конфиг).
- **Видимость адресов** — чёткие правила на сервере до публикации списков.
- **n8n и секреты** — токены GitHub/Gmail только в окружении, не в репозитории.
- **Двойная инфраструктура** — не добавлять карты/геокодирование/Redis до явного требования.
