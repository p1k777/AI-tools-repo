# AGENTS.md — инструкции для AI-агентов

## Проект

Веб-сервис поиска попутчиков для одного маршрута с одной фиксированной конечной точкой. Пользователь просматривает опубликованные поездки и выбирает подходящую. Другая точка задаётся районом из справочника или полным адресом. На первом этапе поиск — это фильтрация объявлений, **не** автоматический подбор попутчиков и **не** расчёт автомобильного маршрута.

Полный список технологий, границ и планируемых расширений: [`docs/tech-stack.md`](docs/tech-stack.md). Перед изменением архитектуры или установкой новых ключевых зависимостей прочитай его.

## Зафиксированный стек

- **Frontend:** React + TypeScript + Vite.
- **UI:** Tailwind CSS + shadcn/ui. Переиспользуй существующие компоненты `src/components/ui`, если они есть; не дублируй компоненты и токены дизайна.
- **Backend:** Python + FastAPI.
- **База данных:** PostgreSQL.
- **Тесты фронтенда:** Vitest + React Testing Library (компоненты); Playwright Test (браузерные сценарии и снимки). При необходимости проверяй доступность через axe-core.
- **AI-прототип:** v0 (макет или компоненты — не источник истины для бизнес-логики).
- **Разработка и отладка:** VS Code + Codex; Playwright MCP / Chrome DevTools MCP — средства исследования и отладки, не замена автотестам.
- **Автоматизация разработки:** n8n + GitHub для AI-ревью Pull Request и обработки Issues. n8n **не** является API приложения.
- **Позднее:** карта на MapLibre GL JS, геокодирование и отдельный сервис маршрутизации. Не добавляй их в MVP без явной задачи.

## Границы MVP

Реализуй только то, что требуется текущей задачей. Приоритетные возможности: список поездок, фильтры по району/направлению/времени, создание поездки, просмотр деталей и (когда потребуется) заявки на поездку. Учитывай одну фиксированную точку и вторую, выбранную из района или адреса.

Подготовь структуру данных к будущей геолокации: различай район, полный адрес и **необязательные** координаты. Не делай карты или автоматическую маршрутизацию обязательными для создания поездки в MVP. Не публикуй полный домашний адрес всем пользователям по умолчанию: предусмотри ограничение видимости точного адреса.

## Правила реализации

1. **Сначала контекст:** перед работой изучи задачу, соответствующую спецификацию и существующие компоненты/API. Если контракт отсутствует, предложи минимальный контракт до его реализации; не выдумывай поведение.
2. **Небольшие изменения:** одна независимая задача — один небольшой логически цельный PR. Не выполняй несвязанный рефакторинг.
3. **Типы и API:** явные TypeScript-типы, единое место для HTTP-клиента, отдельные компоненты представления и запросы к серверу. Источник истины о поездках — FastAPI/PostgreSQL, а не локальные mock-данные.
4. **Интерфейс:** адаптивность, подписанные поля, работа с клавиатуры и видимый фокус; загрузка, пустой список, успех и ошибка. При ошибке отправки сохраняй введённые данные и показывай сообщение.
5. **Формы:** проверяй обязательные поля и неверный ввод; исключай повторную отправку во время ожидания запроса (двойной клик и Enter).
6. **Тесты:** проверяй наблюдаемое пользователем поведение. Подменяй ответы API **в клиентских тестах** (успех, пусто, задержка, ошибка), а демонстрацию выполняй с настоящим API/логикой.
7. **Безопасность:** не коммить секреты и `.env`; не доверяй клиентской валидации, проверяй входные данные и права доступа на сервере.
8. **Не добавляй инфраструктуру заранее:** без прямой потребности не вводи Next.js, SSR, Redux, микросервисы, Redis, PostGIS, карты и сложную маршрутизацию.

## Рабочий цикл: AI → Review → Repeat / Go next

1. **AI / Developer:** реализуй небольшой шаг по критериям приёмки и добавь/обнови тесты. Автор кода может быть человеком или AI.
2. **Review:** проверь diff, типы, сборку, тесты, основные состояния интерфейса и доступность; учитывай AI-ревью через n8n, но не считай его заменой CI и человеческой проверки.
3. **Repeat:** при реальной ошибке — минимальное исправление, повторный запуск относящихся тестов и повторная проверка изменённого кода.
4. **Go next:** только после прохождения проверок и принятия PR переходи к следующей задаче.

В существующем workflow для ДЗ 7.1 `/make_ai_review` должен выполнять первоначальное ревью с дедупликацией проверенного PR; `/make_other_ai_review` запускает другую модель. Команды `/fix_ai_review` и `/rerun_ai_review` — **необязательные будущие расширения**, а не уже реализованное поведение. Автоматические исправления и merge не должны обходить обязательные проверки.

## Условия готовности задачи

- Реализован нужный пользовательский сценарий, а не только статический экран.
- Пройдены необходимые тесты и проверки типов/сборки; нет известных блокирующих замечаний.
- Есть понятные состояния `loading` / `empty` / `success` / `error` и защита от повторной отправки, где применимо.
- Нет несанкционированных изменений стека или публичного раскрытия точных адресов.
- Если меняются API, зависимости, правила или ключевые архитектурные решения, обновлён [`docs/tech-stack.md`](docs/tech-stack.md) и, при необходимости, README.

> Для учебной практики 8 дополнительно сохрани ссылку/экспорт AI-макета, примеры того, что предложил и что исправил AI, результаты запуска клиентских тестов и демонстрацию реального сценария.
